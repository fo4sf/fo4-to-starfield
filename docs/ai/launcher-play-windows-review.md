# Windows review of `launcher.py play` (has not run on the PC)

Author: Grok, 2026-10-22. Status: **offline**. #458 task 6. Base: `main` `180a624` (PR #449).

`launcher.py play` has not run on Windows. Only `watch` ran on the owner's PC, on 2026-10-21 (Claude-cloud, #458). This note reads `System` and `play()` in `src/fo4sf/launcher/crashwatch.py` and compares each named Windows call to Microsoft's documentation. It does not change launcher code. It does not guess game or console facts.

Code under review: `System.open_process` / `wait_exit` / `start_game` / `pids` / `spawn` (`crashwatch.py` 98–145), `apply_papyrus` `os.replace` (316–348), `play` / `_follow` (351–490). Tests use a `FakeSystem` (`tests/test_launcher_crashwatch.py`); they do not call kernel32.

Verdicts: **match** = the code's assumption is what the cited page says. **mismatch** = the page says something the code does not do. **unsure** = the page does not settle it, or it needs a PC run.

| Windows call or behaviour | What the code assumes | What Microsoft / Python docs say | Verdict |
|---|---|---|---|
| `OpenProcess` access rights | `SYNCHRONIZE \| PROCESS_QUERY_LIMITED_INFORMATION` (`0x00100000 \| 0x1000`), `bInheritHandle=False`. That is enough to wait for exit and read the exit code. | [Process access rights](https://learn.microsoft.com/en-us/windows/win32/procthread/process-security-and-access-rights): `SYNCHRONIZE` (0x00100000) is required to wait for the process; `PROCESS_QUERY_LIMITED_INFORMATION` (0x1000) is required for `GetExitCodeProcess`. [OpenProcess](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-openprocess) takes those rights, `bInheritHandle`, and the pid. | match |
| `OpenProcess` refused | Returns NULL; code treats a 0 handle as `None`. `play` then follows the pid with `tasklist` and leaves the exit code unknown (`"no handle on process … the exit code will be unknown"`). Tests: `refuse_handle`. | [OpenProcess](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-openprocess): failure returns NULL; call `GetLastError` (often access denied). The handle is then unusable for wait/exit-code. The fallback path matches that. The code does not log `GetLastError`. | match (error code not recorded) |
| `ctypes` `OpenProcess` return | The integer ctypes returns is a usable `HANDLE` for `WaitForSingleObject` / `GetExitCodeProcess` / `CloseHandle`. | [ctypes return types](https://docs.python.org/3/library/ctypes.html#return-types): foreign functions default to C `int`. [OpenProcess](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-openprocess) returns `HANDLE` (pointer-sized). On 64-bit Windows that can truncate. The code never sets `restype` to `HANDLE` / `c_void_p`. | mismatch |
| `WaitForSingleObject` with `INFINITE` | `0xFFFFFFFF` blocks until the process object is signaled (the game has ended). | [WaitForSingleObject](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-waitforsingleobject): `INFINITE` returns only when the object is signaled. [Terminating a process](https://learn.microsoft.com/en-us/windows/win32/procthread/terminating-a-process): the process object is signaled when the process ends, and open handles stay valid so the exit code can still be read. | match |
| `WaitForSingleObject` return ignored | A successful wait is assumed; `GetExitCodeProcess` runs next even if wait failed. | [WaitForSingleObject](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-waitforsingleobject): `WAIT_OBJECT_0` (0) means signaled; `WAIT_FAILED` (0xFFFFFFFF) means failure (`GetLastError`). The same page warns that an `INFINITE` wait on a thread that creates windows can deadlock. `play` is a console script; whether that thread ever creates a window is a PC fact. | mismatch (return unused); unsure (GUI deadlock) |
| `GetExitCodeProcess` and `STILL_ACTIVE` (259) | After the wait, `GetExitCodeProcess` returns the real exit code into a `DWORD`. Failure (`ok == 0`) becomes `None`. 259 is not special-cased (`exit_name` would print `0x00000103 not a known crash code`). | [GetExitCodeProcess](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getexitcodeprocess): the handle needs `PROCESS_QUERY_INFORMATION` or `PROCESS_QUERY_LIMITED_INFORMATION`. If the process has not ended, success returns **STILL_ACTIVE** (259 / `STATUS_PENDING`). After a successful wait the process has ended, so 259 would be a real exit code; Microsoft says applications should not use 259 as their own exit code. If the wait failed and this call still succeeds, 259 would mean the process is still running. | match after a successful wait; mismatch if wait failed |
| `start_game` Steam (`steam://rungameid/1716740`) | `os.startfile` asks the shell to open the URL and returns at once. `play` then polls `pids()` for `Starfield.exe`. | [os.startfile](https://docs.python.org/3/library/os.html#os.startfile): Windows-only; uses the shell association; returns as soon as the associated application is launched; no wait and no exit status. [ShellExecuteW](https://learn.microsoft.com/en-us/windows/win32/api/shellapi/nf-shellapi-shellexecutew) is that association call (operation `open`). Whether `steam://` is registered, and how long until `Starfield.exe` exists, is a PC fact. | match (immediate return); unsure (handler / delay) |
| `start_game` exe | `subprocess.Popen([Starfield.exe], cwd=starfield)` starts the exe and does not wait. The `Popen` object is dropped; the watcher later opens the process by pid. | [subprocess.Popen](https://docs.python.org/3/library/subprocess.html) on Windows uses [CreateProcessW](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessw). The child keeps running after the parent drops the `Popen`. CreateProcess does not wait for the new process to exit. | match |
| `pids()` via `tasklist` | `tasklist /FI "IMAGENAME eq Starfield.exe" /FO CSV /NH` lists matching pids. CSV rows split on `","`; column 0 is the image, column 1 is the pid. Empty / non-Windows → `[]`. Return code is not checked. | [tasklist](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/tasklist): `/fi "IMAGENAME eq …"`, `/fo csv`, `/nh` are documented. CSV is a listed format. The page does not pin the column order or quoting; the code matches the usual `"Image Name","PID",…` row, including a comma inside the memory field. A failed `tasklist` with empty stdout looks like "not running". | match for the usual CSV row; unsure if `tasklist` is missing or localised |
| `os.replace` over `StarfieldCustom.ini` while it may be open | Write a sibling temp, `os.replace(tmp, path)`. `play` refuses if `Starfield.exe` is already running, so this swap happens with the game closed. `OSError` becomes a `ValueError` that names Controlled Folder Access. | [os.replace](https://docs.python.org/3/library/os.html#os.replace) on Windows replaces `dst` if it is a file. [Moving and replacing files](https://learn.microsoft.com/en-us/windows/win32/fileio/moving-and-replacing-files): a file must be closed before it can be moved; [MoveFileEx](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexw) with `MOVEFILE_REPLACE_EXISTING` fails (return 0, `GetLastError`) when the destination cannot be replaced. An INI held open by another process is that case. CFA blocking Python in Documents is a separate Windows ACL/policy failure, which the `OSError` path already names. | match (game closed first; replace can still fail if another process holds the file) |
| `subprocess.Popen` holding the `wb` handle for ProcDump's report | `with open(out_path, "wb") as log: return Popen(..., stdout=log, stderr=STDOUT)`. Comment: the child keeps its own copy. After `Popen` returns, the `with` closes the parent's file. Later `fold_output` reads the path when ProcDump has exited. | [subprocess](https://docs.python.org/3/library/subprocess.html) 3.7+: on Windows `close_fds` defaults to True even when redirecting; redirected standard handles are still passed to the child. [Handle inheritance](https://learn.microsoft.com/en-us/windows/win32/sysinfo/handle-inheritance): the child receives a duplicate; the parent can close its copy. Closing the parent `wb` after `Popen` leaves ProcDump as the remaining writer, so `fold_output` can open the file after ProcDump exits. | match |

Both mismatches (the HANDLE restype and the unused WaitForSingleObject result) were fixed in #471, merged as `ccab047`.

## First `play` checks on the PC

These are the first things to watch when `play` actually runs. They are not pass/fail claims.

1. `play --dry-run` prints the plan and exits 0 only after its preflight passes. A bad setting, a missing exe or ProcDump, low dump space, or a game already running each make it refuse with exit 2.
2. With Starfield already running, `play` refuses before any INI or process start.
3. `route=exe`: `Starfield.exe` is created from the install folder; `tasklist` sees that image before `start_timeout_s`.
4. `route=steam`: the shell opens `steam://rungameid/1716740`; `Starfield.exe` appears in time, or play reports it did not stay up. Note the delay. Do not treat Steam's own error boxes as a Windows API result.
5. If the console says `no handle on process` (printed to the console, not written to `crashwatch.log`): `OpenProcess` was refused (integrity / access). The exit code will be unknown; confirm whether that print appears on a normal unelevated Python vs an elevated game.
6. After a normal quit, play should unblock from `WaitForSingleObject` and print an exit code. 0 is documented here as "normal exit (also what a silent ExitProcess gives)" — a PC run is what tells those two apart, not this note.
7. If the printed code is `0x00000103`, treat it as the STILL_ACTIVE collision until it is known whether the wait returned `WAIT_OBJECT_0`.
8. Papyrus on/off: if Documents is blocked, the refusal names Controlled Folder Access and the game is not started. If an editor has `StarfieldCustom.ini` open, expect the same `OSError` path.
9. Watcher on: after `settle_s`, `crashwatch.log` should say `armed` or `NOT armed` with ProcDump's reason. Leave ProcDump running if play says a dump is still being written.
10. Unique `procdump_<pid>_<unix>.out` is folded into `crashwatch.log` after ProcDump exits; the parent must not still hold the `wb` handle (the `with` is what drops it).
